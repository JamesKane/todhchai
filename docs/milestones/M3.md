# M3: Native tier 0

The native track's first milestone on croi ([../roadmap.md](../roadmap.md),
"M3"). N0 built its services hosted, over a kernel that copies croi's
object model; here they move onto croi by changing the kernel underneath
them, and devmgr, the drivers and the console join them.

croi reaches user space at K8b: userboot starts `userboot.next=` from a
Zircon-format bootfs and passes Zircon's processargs. M2's exit and its
kernel budgets are K8c. What croi has and lacks is in
[../croi-requirements.md](../croi-requirements.md) (status as of
2026-10-10) and
[../research/croi-assessment-2026-10-10.md](../research/croi-assessment-2026-10-10.md).

The steps are in two parts. M3a–M3f need only M2: N0's boot running natively
on a ramdisk, and its trace. M3g onwards need croi work past M2 (croi's K9), named in each step:
resources and interrupt objects (item 13), a BTI with no IOMMU (item 14),
syscalls for physical and contiguous VMOs and cache operations (item 7),
and firmware data for user space (item 20).

**Exit** (the roadmap's):
- Boot to a framebuffer text console in QEMU (amd64, KVM).
- Mount a Taisce volume on virtio-blk, write files with attributes, and get
  a live query update for them: N0's exit, natively, on a real device.
- M3's system budgets ([../performance.md](../performance.md)) met in QEMU:
  kernel entry to the console, spawn to `main`, a cached 4 KiB read through
  the namespace, a live query update, the shared-memory ring and futex
  budgets, and resident memory. A0's ACPI budgets, measured again in QEMU.
- In `td ci`: the native boot under QEMU with KVM, beside both existing
  builds.

## Decided for this stage (2026-10-10)

1. **The tier 0 runtime is ours** (`libsys`, as the roadmap names it): entry
   and processargs, a heap over VMOs, stdout over debuglog, the stack guard,
   in Swift where Swift can do it, with our libc's `mem*` (`lib/libc`) and
   only the entry stub in assembly. croi's user runtime stays croi's test
   harness; Todhchai's process start-up is Todhchai's.
2. **Todhchai tracks croi's head.** `td` builds croi's loader and kernel
   from `../croi`'s last commit, exported to `build/croi/src` (decided in
   M3g: never the working tree, which croi's own work leaves unbuildable
   between commits), and takes croi's ABI values from there; there is no
   pin. The two projects will become one repository later. A croi commit
   that breaks the native boot shows up in `td ci` at once.
3. **amd64 boots; arm64 and rv64 build.** `td ci` boots amd64 under KVM and
   builds tier 0 for all three; `td boot --arch` boots the others on
   request, until a later milestone makes them gates.

## Steps

| Step | Content | Status |
|---|---|---|
| M3a. Building for croi | `td boot`: croi built from `../croi` as checked out (`build/croi/<arch>`), our tree with the `native-<arch>` presets (`cmake/croi.cmake`), a bootfs of `build/native-<arch>/bin` (`lib/bootfs`: Zircon's format, byte-identical to croi's `mkbootfs.py`), the ESP with `userboot.next=bin/launcher`, QEMU (KVM on amd64); `--test` judges userboot's report. libsys (`lib/sys/native`): `_start` and the syscall instruction in assembly; processargs (arguments, environment, startup handles), stdout over debuglog and a heap over VMOs (size classes, large blocks mapped alone) in Swift; our libc's `mem*`/`str*` under their C names. Swift's Unicode tables are linked (the toolchain's), so `String ==` works; rv64 is `lp64` to match them. `bin/launcher` checks its runtime and exits 0, 2.6 s from power on under KVM; `td ci` builds all three arches and boots amd64 | Done |
| M3b. `Sys` over croi | The native backend (`lib/sys/backend/native`): every `Sys` call as a croi system call, the clock from croi's vDSO. `Thread.start` keeps its closure: the backend maps each thread a stack and starts it at a trampoline, and a finished thread's stack is unmapped by the next start (croi can't unmap a stack as its thread exits). New in both backends: `Lock` and `Futex` (a three-state futex lock; no owner yet, as croi's threads have no thread pointer to name themselves with), `Process.current`, `Thread.spawn` and `join`, and unmapping with a length; the hosted kernel gains futexes and `processSelf`, and threads spawned in its host process no longer end it. libsys's own lock moves onto futexes. `bin/sys-test` (`tests/native`) runs every call on croi, M2's exit sequence among them, in `td ci`; it passed 10 of 10 boots on amd64. `Process.create`'s root VMAR comes with M3d, which needs it, and tier 0 code leaves pthreads in M3c | Done |
| M3c. The services in Embedded Swift | The trace writer, the IPC runtime, Node, the launcher, block (less its image-file backend) and fs are tier 0: in both CMake builds, and held to strict memory safety in SwiftPM too. CMake loads the `@IPCLibrary` macro's plugin from SwiftPM's build. Off Glibc and pthreads onto `Sys`: `Lock`, `Locked<Value>` (for Synchronization's Mutex, which croi's targets lack), `Thread.spawn`, `Clock.realtime` (natively the monotonic clock until croi has UTC). No `weak` or `unowned` in Embedded Swift: Node's and fs's sessions say when they close, and the cycles that strong references make are broken where their owners end. No hashed collections on reachable paths (the dispatcher's table is a sorted array; Embedded's need `ceil` and a random seed); the launcher's program table changes in M3d. The trace records nothing natively until M3e. `bin/services-test` (`tests/native`) runs on croi, in one process: Node through a namespace, then the block service over memory, Taisce's fs service over its ring, typed attributes and a live query's update; on all three arches, and in `td ci`. The native backend rounds VMO sizes and mapping lengths up to pages, which croi requires | Done |
| M3d. The launcher, natively | `bin/launcher` is lib/launch on croi: it reads bootfs's directory (not the whole image), takes every `bin/NAME` as a program and launches every `etc/manifests/*.manifest`, a job and a process per service, restarts by policy, `/svc` per process. `Process.start` natively loads an ELF from a VMO (`lib/sys/backend/native/Loader.swift`, as croi's userboot does: read-only segments mapped from bootfs's pages, writable ones copied, a stack from PT_GNU_STACK) and hands the process processargs with its own process, thread and root VMAR, a debuglog for stdout, and the Startup channel as `PA_USER0`; no job, resource or bootfs. The root VMAR that `process_create` returns is kept by the process's koid until it starts. `lib/elf` (tier 0) reads ELF64 executables from a file's first bytes. The launcher's program table is a list, not a Dictionary. `td boot --manifests DIR --cmdline WORDS` puts manifests in bootfs and words on croi's command line; with `launcher.until=SERVICE` the launcher exits with that service's code. `td ci`'s boot is the launcher's test (`tests/native/manifests`): `launch-test` checks its sealed namespace holds only `/svc/tree`, reads `tree`, crashes it and reads the restarted instance through the same path (7 ms from launch to the first read, 27 ms to the restarted one, KVM). libsys's self-checks moved to `sys-test` | Done |
| M3e. N0's boot on croi | block, fs and `catalog` are native programs in bootfs over the bodies both boots share (`lib/services`, tier 0; the hosted programs wrap them). block serves a ramdisk (`VMOBackend`: a VMO mapped, nothing touched up front; `boot/native/block.manifest`); fs's new volume takes its UUID from the clock and its koid until croi has a random source. `bin/n0-exit` (`tests/native`) is N0's exit test on croi, driving the launcher as the hosted test does: the catalogue and live query through /svc/fs, the trees read like files, fs killed, restarted and the client reconnected, a manifest naming a missing service refused; in `td ci` (`td boot --next bin/n0-exit --manifests boot/native`). It measures, in the guest, on the monotonic clock (KVM): spawn to `main` 178 µs (`bin/spawn-probe`; budget 200 µs), opening and reading a cached file 13.6 µs (budget 5 µs: not met), a live query's update 33 µs (budget 1 ms), the launch of all three 5.9 ms, fs's restart 3.2 ms. Measuring found the native backend reading every channel message into a 64 KiB buffer that the heap mapped and unmapped each time (137 µs a read, 270 µs a call): reads are now sized first (croi leaves the message queued when the buffer is too small), calls' reply buffers aren't zeroed, and the heap's classes reach 128 KiB (a call to another thread is 3 µs). `sys-test` reports the clock, a local write and read, and a call | Done |
| M3f. The native trace | `TraceSession` (`lib/trace/session`) starts croi's kernel trace and gives each traced process a region (a VMO in processargs, `PA_USER1`; the launcher's `extraStartupHandles`), which the native writer maps (`lib/trace/writer/native`). libsys gives each thread a block through croi's new thread pointer (FS's base on amd64, `TPIDR_EL0`, `tp`), where a thread's ring is kept. Out of the guest, decided: the debuglog, in base64 lines paced below the console's ~110 KB/s (croi drops debuglog records when its console falls 512 behind), reassembled by `td boot` into `bench/out/boot/<arch>/trace` (a missing piece fails the boot); `td boot --keep-croi` boots the croi last built, as croi's tree is edited beside us. `td trace summary DIR` joins every file into one timeline: a call's path through client, croi's CHANNEL_WRITE, CHANNEL_READ and DONATE, and server (`TraceSet`). `n0-exit` records with `--cmdline n0.trace=CATEGORIES`, in `td ci`. The cached read (15.7 µs traced) is two calls, walk (6.3 µs) and read (7.2 µs); in a read, croi's write until the server reads is 1.2 µs, the server's dispatch 0.5 µs, fs's work 3.5 µs, the reply until the client has it 1.5 µs: about 3 µs a call crossing croi, so the 5 µs budget needs fewer calls (an open that returns data), not only a faster fs. Not yet: user and kernel thread ids joined (croi's task ids aren't visible to user space) | Done |
| M3g. devmgr and PCI | `Sys` gains croi's K9a calls: `Resource.create`/`info`, `VMO.physical` and `setCachePolicy`, `IOPorts` (amd64's `in`/`out` in libsys's assembly); `sys-test` reads q35's host bridge through a physical VMO over its ECAM page and through ports 0xCF8/0xCFC. Manifests grant hardware: `resource KIND` (the launcher's ranged roots, which userboot passes) and `programs` (bootfs and a job under the service's), decided here, as is devmgr running its driver hosts with lib/launch. `lib/pci` (tier 0): configuration space, ECAM through `_Volatile`, enumeration across bridges with BARs sized and capabilities walked; `MCFG` in TDACPI. `lib/devmgr`: devices, bind rules as Swift predicates (`Rules.swift`, first match), the resources a host is granted (a resource per BAR, one over its 4 KiB of ECAM; `HandleType.device`). `bin/devmgr` maps ECAM (`--ecam`, until K9b's MCFG), enumerates, turns on decoding for bound functions and starts a host per device, its tree under `drivers/`; `bin/edu`, the first driver (QEMU's edu device), checks its id, liveness, a factorial, its config space, and that its resource reaches no further than its BAR. `td ci` boots `devices-test` with `-device edu`. In QEMU (KVM): mapping 256 buses' ECAM 2.6 ms, finding q35's 7 functions 3.4 ms (about 450 configuration accesses, each a VM exit). `td boot` builds croi's last commit, not its working tree (decision 2, revised) | Done |
| M3h. ACPI natively | croi's K9b gives userboot its boot data, firmware's items in Zircon's ZBI format; `lib/zbi` (tier 0) reads them (RSDP, SMBIOS, framebuffer, memory ranges) from croi's zbi.h. Manifests grant it with `bootdata`. devmgr reads the tables from the RSDP through physical VMOs a page at a time (croi refuses one only partly over firmware memory), takes ECAM from the MCFG (`--ecam` stays as an override), and loads ACPI's namespace with our AML interpreter, its regions over the machine (`lib/devmgr/Firmware.swift`: SystemMemory through those pages, SystemIO through I/O ports requested as touched, PCI_Config through ECAM), runs _INI and lists the present devices beside the PCI functions; bind rules can match HIDs and CIDs (`DriverRule.acpi`). On q35: 7 tables, 279 nodes, load 0.7-1 ms, 39 of 40 devices present; the HPET is absent, as croi keeps its registers (its clock), so its _INI fails on a refused region. A hosted test runs q35's DSDT through devmgr's host: the PIRQ registers decide the links' _STA, the HPET's registers its presence. A0's budgets on croi (KVM), `bin/acpi-bench` over this machine's 587 KiB of tables (`td boot --data DIR` puts them in bootfs; in `td ci` when the corpus is here): load median 2.3 ms, p99 4.1 ms (budget 5 ms); _STA on 162 devices median 117 µs, p99 181 µs (budget 1 ms) | Done |
| M3i. virtio-blk | Done so far (croi K9c): `Sys.Interrupt` (create under an IRQ resource, bind to a port made `bindToInterrupt`, ack, wait, virtual, affinity), checked in `sys-test`. devmgr routes PCI interrupts through ACPI: \_PIC(1), the root bridge's _PRT, each link's _CRS to a GSI and trigger mode (`lib/devmgr/Routing.swift`; q35: GSIs 16-23, level-high), and grants a host an IRQ resource for its pin (`resource irq` in devmgr's manifest; `HandleType.device` 0x100 + the mode). `bin/edu` takes its device's interrupt 100 times: GSI 23, raise to wake median 33-37 µs, croi's fire to wake 12-14 µs (KVM). `lib/virtio` (tier 0): the PCI transport (vendor capabilities, the common configuration, reset and feature negotiation as §3.1.1 orders it, config_generation), split virtqueues, virtio-blk's requests, tested against a model device that serves requests from the rings. `bin/virtio-blk` binds modern and transitional virtio-blk, maps only the BARs its capabilities name, negotiates (VERSION_1, BLK_SIZE, FLUSH) and reads the capacity: in `td ci`, a 64 MiB disk that reads as zeros (QEMU's null-co, modern only) and the ESP. The block service's backend over it (`VirtioBlockBackend`, lib/virtio): 4 KiB blocks as eight sectors, requests through queue 0 and a bounce region, one at a time, notified through the notify capability, completion by a `wait` (the interrupt natively); memory the device reaches comes from a `DMAMemory`. Tested hosted against the model device, Taisce formatted, written, mounted again and checked on it. Then (croi K9e) `Sys.DMA`: the stub IOMMU, BTIs with croi's narrowing properties, pins and PMTs, contiguous VMOs, checked in `sys-test`. devmgr makes the stub IOMMU (`resource system`) and grants each bound device a BTI (id: bus, device, function), narrowed to its rule's address width (edu 28 bits); croi logs each as a no-IOMMU trust decision. `PinnedMemory` (lib/virtio) gives the backend contiguous VMOs, mapped and pinned. `bin/virtio-blk` serves the block service itself (`Services.block`), woken by its INTx interrupt from a port with a 50 ms deadline (a lost interrupt costs a poll, not a hang), the ISR read to lower the line. In `td ci`'s devices boot, a 64 MiB disk image made afresh each run at 00:10.0: fs makes the volume "main" on it through devmgr's tree (`mount /disk devmgr/drivers/virtio-blk-00:10.0`), and N0's catalogue writes its songs and sees its live query's update; 18 reads, 33 writes, 6 flushes, no errors. Left for later: MSI-X (K9d) in place of INTx; requests in flight together and zero-copy (the bounce region); a host's death resetting its device and releasing the BTI's quarantine (croi keeps a killed host's pins quarantined, as it should); slots behind bridges | Done |
| M3j. The framebuffer console | `bin/console` maps the GOP framebuffer from croi's boot data (a physical VMO under an MMIO resource, write-combining) and shows the system's log: it reads croi's debuglog with the debuglog system resource (`resource system`; `Debuglog` in Sys), a record a line as croi prints them, warnings amber and errors magenta, plus text written to its `write` leaf (`screen` reads the grid back). `lib/console` (tier 0): a text grid (UTF-8, wrapping, scrolling, tabs, escapes dropped) and a renderer that composes each pixel line and writes it in one run, redrawing from the grid when it scrolls (write-combining memory is slow to read). The font is Spleen 2.1.0 (decided: BSD-2-Clause, `data/fonts/spleen` with its provenance), 8x16 or 16x32 on framebuffers 2560 wide or more; `fontgen` writes it as a table that keeps Spleen's license. The desktop's colors: phosphor on bg.0. On q35 (KVM, 1280x800, 160x50 cells): the first frame 3 ms after the console starts, at 1.87 s on the monotonic clock, which starts at kernel entry: croi's boot self-tests take nearly all of it, so the 100 ms budget is croi's to meet (K9f); a full redraw about 1.1 ms. `devices-test` writes to it and finds its text and the log on the screen | Done |
| M3k. The other virtio devices | A driver host each for QEMU's network, input, GPU and sound devices (`bin/virtio-net`, `-input`, `-gpu`, `-sound`; bind rules for their modern ids, and network's transitional one), over `lib/virtio`'s `PCIDevice` (the capabilities, only the BARs they name) and one scaffold compiled into each (`boot/programs/virtio-host`), which virtio-blk now uses too. Each negotiates and reads its device's configuration: network its MAC, link status, MTU and queue pairs; input asks its configuration for the name, ids and event types (a keyboard and a tablet); the GPU its scanouts and capsets, with EDID; sound its jacks, PCM streams and channel maps. Tested hosted against model devices, and in `td ci`'s devices boot with all of them (net on QEMU's user network with a fixed MAC, sound on a silent audiodev). Their queues, and so packets, events, display commands and PCM, wait for DMA (croi's K9e), and the services over them are M4's | Done |
| M3l. The exit | The exit above, all budgets in `td bench` | To do |
