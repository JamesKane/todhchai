# M3: Native tier 0

The native track's first milestone on croi ([../roadmap.md](../roadmap.md),
"M3"). N0 built its services hosted, over a kernel that copies croi's
object model; here they move onto croi by changing the kernel underneath
them, and devmgr, the drivers and the console join them.

croi reaches user space at K8b: userboot starts `userboot.next=` from a
Zircon-format bootfs and passes Zircon's processargs. M2's exit and its
kernel budgets are K8c. What croi has and lacks is in
[../croi-requirements.md](../croi-requirements.md) (status as of
2026-10-10) and
[../research/croi-assessment-2026-10-10.md](../research/croi-assessment-2026-10-10.md).

The steps are in two parts. M3a–M3e need only M2: N0's boot running natively
on a ramdisk. M3f onwards need croi work past M2, named in each step:
resources and interrupt objects (item 13), a BTI with no IOMMU (item 14),
syscalls for physical and contiguous VMOs and cache operations (item 7),
and firmware data for user space (item 20).

**Exit** (the roadmap's):
- Boot to a framebuffer text console in QEMU (amd64, KVM).
- Mount a Taisce volume on virtio-blk, write files with attributes, and get
  a live query update for them: N0's exit, natively, on a real device.
- M3's system budgets ([../performance.md](../performance.md)) met in QEMU:
  kernel entry to the console, spawn to `main`, a cached 4 KiB read through
  the namespace, a live query update, the shared-memory ring and futex
  budgets, and resident memory. A0's ACPI budgets, measured again in QEMU.
- In `td ci`: the native boot under QEMU with KVM, beside both existing
  builds.

## Decided for this stage (2026-10-10)

1. **The tier 0 runtime is ours** (`libsys`, as the roadmap names it): entry
   and processargs, a heap over VMOs, stdout over debuglog, the stack guard,
   in Swift where Swift can do it, with our libc's `mem*` (`lib/libc`) and
   only the entry stub in assembly. croi's user runtime stays croi's test
   harness; Todhchai's process start-up is Todhchai's.
2. **Todhchai tracks croi's head.** `td` builds croi's loader and kernel
   from `../croi` as it is checked out, and takes croi's ABI headers from
   there; there is no pin. The two projects will become one repository
   later. A croi change that breaks the native boot shows up in `td ci`
   at once.
3. **amd64 boots; arm64 and rv64 build.** `td ci` boots amd64 under KVM and
   builds tier 0 for all three; `td boot --arch` boots the others on
   request, until a later milestone makes them gates.

## Steps

| Step | Content | Status |
|---|---|---|
| M3a. Building for croi | `td boot`: croi built from `../croi` as checked out (`build/croi/<arch>`), our tree with the `native-<arch>` presets (`cmake/croi.cmake`), a bootfs of `build/native-<arch>/bin` (`lib/bootfs`: Zircon's format, byte-identical to croi's `mkbootfs.py`), the ESP with `userboot.next=bin/launcher`, QEMU (KVM on amd64); `--test` judges userboot's report. libsys (`lib/sys/native`): `_start` and the syscall instruction in assembly; processargs (arguments, environment, startup handles), stdout over debuglog and a heap over VMOs (size classes, large blocks mapped alone) in Swift; our libc's `mem*`/`str*` under their C names. Swift's Unicode tables are linked (the toolchain's), so `String ==` works; rv64 is `lp64` to match them. `bin/launcher` checks its runtime and exits 0, 2.6 s from power on under KVM; `td ci` builds all three arches and boots amd64 | Done |
| M3b. `Sys` over croi | The native backend (`lib/sys/backend/native`): every `Sys` call as a croi system call, the clock from croi's vDSO. `Thread.start` keeps its closure: the backend maps each thread a stack and starts it at a trampoline, and a finished thread's stack is unmapped by the next start (croi can't unmap a stack as its thread exits). New in both backends: `Lock` and `Futex` (a three-state futex lock; no owner yet, as croi's threads have no thread pointer to name themselves with), `Process.current`, `Thread.spawn` and `join`, and unmapping with a length; the hosted kernel gains futexes and `processSelf`, and threads spawned in its host process no longer end it. libsys's own lock moves onto futexes. `bin/sys-test` (`tests/native`) runs every call on croi, M2's exit sequence among them, in `td ci`; it passed 10 of 10 boots on amd64. `Process.create`'s root VMAR comes with M3d, which needs it, and tier 0 code leaves pthreads in M3c | Done |
| M3c. The services in Embedded Swift | The IPC runtime and generated code, Node, `Namespace`, the launcher, block, fs and the trace writer join the Embedded builds: off Glibc and pthreads onto `Sys`; no hashed collections (or `ceil` from our libc); existentials and key paths checked. Each library's smoke program runs on the host Embedded build | To do |
| M3d. The launcher, natively | ELF loading from bootfs into a new process (tier 0 ELF reader; text mapped from the bootfs VMO, data copied), processargs with the Startup channel as a `PA_USER0` handle, manifests read from bootfs, a job per service, restart policies, `/svc` | To do |
| M3e. N0's boot on croi | block over a ramdisk (a bootfs VMO), fs, and `catalog`, natively; N0's exit test in QEMU under `td ci`, kill and reconnect included. The native trace: user rings beside croi's kernel rings in one trace, so a call's flow joins croi's CHANNEL and DONATE records with ours; `td trace` reads it. Spawn to `main`, the cached read and the live query measured here | To do |
| M3f. devmgr and ACPI | devmgr and driver hosts; the ACPI tables and AML's operation regions through croi (item 20); our AML interpreter (A0) loading the machine's namespace; PCI over ECAM. A0's budgets in QEMU. *Needs croi items 13 and 20* | To do |
| M3g. virtio-blk | The virtio PCI transport and a virtio-blk driver behind the block service's backend; DMA through a BTI with no IOMMU. Taisce on it. *Needs croi items 13 and 14 and the VMO syscalls* | To do |
| M3h. The framebuffer console | The GOP framebuffer (item 20) mapped write-combining, a text console with a bitmap font (data with provenance), kernel entry to console measured. *Needs croi item 20* | To do |
| M3i. The other virtio devices | net, input, gpu-2d and sound, each to a driver that answers its device, ready for M4's services | To do |
| M3j. The exit | The exit above, all budgets in `td bench` | To do |
