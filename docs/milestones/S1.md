# S1: Taisce "CoW", hosted

Taisce's second stage ([../filesystem.md](../filesystem.md) §2): crash
consistency and integrity. The change journal, index format and transaction
API stay as S0 made them; S1 replaces the commit layer beneath them. The
roadmap places S1 in M9. It's started now, hosted, while croi works toward
M2, and M3 mounts whatever stage Taisce has reached.

**Exit:**
- Every block's BLAKE3-128 checksum is verified on read. A flipped bit
  anywhere is reported, never silently used, and `fsck.taisce` scrubs the
  whole volume.
- A transaction group commits by superblock flip: no write-ahead log for
  metadata. The crash harness, shadow-model fuzzer and query fuzzer pass
  unchanged in intent, and corruption tests join `td ci`.
- `fsync` is durable through the intent log without waiting for a group
  commit.
- Readers run lock-free beside the writer, with epoch-based reclamation.
  A concurrency test runs readers against a writer and checks every
  snapshot they see is consistent.
- Budgets, from traces: `fsync` latency; commit time per group; the cached
  read with checksums (S0's 5 µs target still holds); reader scaling.

| S1d. | S1e. The intent log | `fsync` writes the operations since the last commit (their batches, and the blocks they allocated and freed) as checksummed records and returns. Mount replays them on top of the last commit. Crash tests cover the log. **Done:**<ul><li>An intent region after the bitmaps holds 1% of the volume, between 1 and 16 MiB (on-disk version 4).</li><li>The engine keeps each applied batch as an `IntentOp`, with the file blocks the file system allocated for it and freed after it (B+tree nodes rebuild themselves on replay).</li><li>`fsync` writes the pending operations as one BLAKE3-checked record, stamped with the committed txg it builds on and a seq, then a barrier, which also covers the file data. | S1f. Lock-free readers | The writer publishes an immutable root after each operation; readers walk it without locks; replaced nodes and freed blocks wait in per-epoch limbo until no reader is older, with back-pressure when limbo grows (gefs's scheme). A concurrent test, and the hosted FUSE server reading on several threads. **Done:**<ul><li>**Snapshots.** After each batch and commit, the writer publishes an immutable `Snapshot`: every tree's root and the group's changed nodes. The nodes are kept in 64 sorted buckets shared copy-on-write, so publishing copies one bucket and the outer array, not every node.</li><li>**Epochs** (`EpochManager`, Synchronization atomics, Embedded-clean). 64 reader slots; a reader announces the epoch while it reads; the writer advances only when no reader is behind. Replaced snapshots and retired blocks wait in limbo until the epoch is two past theirs.</li><li>**Allocator.** Blocks past their deferral are *retired*, not free, until the engine releases them. Once readers are on, file blocks a snapshot can see are pinned (as for the intent log), so they're never rewritten in place.</li><li>**Back-pressure.** More than 1024 retirements in limbo, or a batch or commit short of space while limbo holds blocks: the writer waits for readers (spinning: their snapshots are short), then goes on.</li><li>**Batches roll back exactly.** A failed batch used to be undone by re-applying old values, which itself needs space. On a nearly full volume it could fail half-way, or leak a node a split had allocated (the concurrent test found both). Now a batch, and a commit's in-memory phase, keep the roots and changed nodes as they were (shared, so cheap) and the allocator words they change, and put them back.</li><li>**One read path.** Stat, lookup, readlink, names, path, list, read and attributes are written once on `FileReading`, which `FileSystem` (the writer) and `FileReader` (a reader thread) both conform to. A reader's caches keep each node and block with the checksum it was verified against, and a hit must match the snapshot's, so they never need invalidating.</li><li>**FUSE.** `startReaders(n)` (4 in `taisce-fuse`): reader threads read every request, answer lookups, getattr, reads, readlink and xattrs themselves, and pass the rest to the one writing thread through a queue. A file handle is its inode with the top bit set, so readers share no handle table.</li><li>**Tests:**<ul><li>a snapshot outlives six rewrites and commits and 3 MB of new data, and still reads its version;</li><li>four readers with one-entry caches against a writer on a nearly full volume (writes, renames, a counter, fsyncs, commits): every read is one version whole, the directory never gains or loses a name, the counter never goes back, 20 ms holds see nothing change, and limbo drains and `check` passes afterwards;</li><li>a batch that runs out of space part-way leaves contents and free space exactly as they were;</li><li>three reader threads behind a socket pair answer reads and getattrs between writes, and none is torn;</li><li>the live mount runs with four readers.</li></ul></li><li>Mutation-checked: no limbo for blocks, no pinning, and readers that don't announce their epoch all fail the concurrent tests; undo by re-applying fails the out-of-space test. The concurrent test needed tiny reader caches, a nearly full volume and long holds before it caught the first and third.</li><li>Later:<ul><li>a writer short of space for reasons other than limbo (blocks held for the group) reports `noSpace` rather than committing to reclaim them;</li><li>readdir still goes to the writer;</li><li>each reader thread has its own caches.</li></ul></li></ul> | Done |

## Decided for this stage (2026-10-09)

1. **The checksum is BLAKE3, truncated to 128 bits.** It's our own,
   written once for both Taisce and the crypto stack (architecture §17). S2's
   dedupe and encryption want a hash that can't be collided on purpose. The
   alternative was xxh3-128, faster but not cryptographic.
2. **Lock-free readers are part of S1**, so M3's `fs` service inherits them.
   The alternative was deferring concurrency to S3.
3. **Physical block pointers, not an object map.** A child pointer is
   (address, BLAKE3-128, birth txg), as ZFS and gefs do. S2's snapshots use
   deadlists keyed by birth txg, which these pointers carry, and clones are
   per-extent refcounts. There's no lookup per read and no second
   structure to persist. Moving a node rewrites its path to the root.
   filesystem.md §3 is updated.
